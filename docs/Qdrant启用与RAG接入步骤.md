# 知言 AI：Qdrant 后续启用与 RAG 接入步骤

> **进度更新（2026-10-03）：** 本文后半部分是接入前的设计记录，其中“尚未接入”的描述已经过时。当前实现与启用步骤请以 [RAG 检索与三模式使用说明](RAG检索与三模式使用说明.md) 为准。

更新日期：2026-09-23

适用环境：Windows PowerShell、Docker Desktop、当前项目的 Vue 前端与 FastAPI 后端。

## 先明确当前进度

你已通过 Qdrant 健康检查，并能打开管理界面，说明**向量数据库服务已经运行**。但目前项目代码仍是“上传附件后，把提取的文档正文放进模型上下文”的问答方式；`backend/app/config.py` 中还没有 Qdrant 配置，后端依赖中也没有 Qdrant 客户端。因此，现在启动知言 AI 不会自动把文件写入 Qdrant，也不会进行向量检索。

本文包含两部分：先记录已安装 Qdrant 的日常启用方法，再给出后续接入 RAG 的实施顺序。后半部分是**待实施方案**，不是声称已有的功能。本文不要求现在修改 `.env`、创建集合或迁移数据库。

## 一、以后每次开机如何启用

1. 启动 **Docker Desktop**，等待界面显示引擎已运行。
2. 打开 PowerShell，查看容器状态：

   ```powershell
   docker ps -a
   ```

3. 如果之前按安装方案将容器命名为 `zhiyan-qdrant`，并且状态为 `Exited`，启动它：

   ```powershell
   docker start zhiyan-qdrant
   ```

   如果状态已经是 `Up`，不用重复启动。若你安装时使用了别的容器名，以 `docker ps -a` 显示的实际名称为准。此前建议的 `--restart unless-stopped` 会让容器在 Docker 引擎重新启动时自动恢复，但手动停止过的容器仍可能需要手动启动。

4. 验证 Qdrant：

   ```powershell
   Invoke-RestMethod http://127.0.0.1:6333/healthz
   Invoke-RestMethod http://127.0.0.1:6333/collections
   ```

   健康检查通过即可；`collections` 为空表示尚未创建向量集合，不是故障。管理界面地址为 <http://127.0.0.1:6333/dashboard>。

5. 照常启动现有项目。以下命令分别在**项目根目录**和另一个 PowerShell 窗口运行：

   ```powershell
   .\venv\Scripts\python.exe -m uvicorn app.main:app --app-dir backend --reload
   ```

   ```powershell
   Set-Location frontend
   pnpm dev
   ```

   **当前版本即使 Qdrant 没启动，也不影响原有聊天与附件问答**，因为后端尚未连接它。等 RAG 实现后，再把 Qdrant 视为相关功能的启动前置条件。

排查时可运行 `docker logs --tail 50 zhiyan-qdrant`；如果实际容器名不同，替换命令中的名称。`docker version` 能帮助区分“PowerShell 找不到 Docker”和“Docker Desktop 引擎未启动”。不要为了重试而删除命名卷或执行 `docker volume prune`，那可能清掉向量数据。

## 二、接入 RAG 前先定范围

建议第一版只做**当前登录用户、当前聊天会话中的文档检索**：上传的 TXT、Markdown、文字型 PDF、DOCX 可以被切分和索引；问题到来时，只检索当前会话允许使用的文档。图片仍走现有视觉模型通道，不因为安装了 Qdrant 就自动具备“按图像内容搜索”的能力。跨会话个人知识库、OCR 扫描件和图片向量检索留到后续版本。

这个范围与当前实现一致：附件由 `backend/app/attachments/` 管理，聊天消息在 `backend/app/conversations/` 保存；现有 `attachments` 和 `message_attachments` 表已经记录附件所属用户及消息关联。检索范围必须由后端根据已登录用户和会话里的合法附件计算，不能相信浏览器直接提交的 `user_id` 或任意附件 ID。Qdrant 中的 `user_id` 等 payload 只是辅助过滤，不能代替后端权限校验。

## 三、建议的开发顺序

| 阶段 | 要完成什么 | 主要落点与验收结果 |
| --- | --- | --- |
| 1. 选 Embedding 模型 | 确定使用哪个文本向量模型、API 地域、输出维度和费用；先用短文本验证能得到稳定维度的向量 | 在方案中固定模型与维度。**维度确定前不创建正式集合**；换模型或维度通常需要重建索引 |
| 2. 增加配置与依赖 | 后端增加 Qdrant 地址、集合名、Embedding 配置和开关，使用本地环境变量，密钥只留后端 | `backend/app/config.py`、`backend/.env.example`、`backend/requirements.txt`；现有真实 `backend/.env` 只补充，不覆盖 |
| 3. 文档切分与入库 | 复用已有附件解析结果，把正文按合理长度与重叠切成片段，批量生成向量，写入 Qdrant | 建议新增独立的 RAG 包，例如 `backend/app/rag/`；相同附件重试不产生重复片段；保存附件 ID、片段序号、来源页码（能确定时） |
| 4. 索引状态与恢复 | 记录待索引、索引中、完成、失败及模型版本；出错可重试，不让“上传成功”被误认为“已可检索” | SQLite 通过**新迁移脚本**增加最少的索引状态数据；不要直接手改已有数据库或重建账号表 |
| 5. 检索并回答 | 对用户问题生成查询向量，在 Qdrant 里按当前用户和授权附件范围过滤，取回相关片段，再将片段与问题送给现有聊天模型 | 接入点在 `backend/app/conversations/service.py` 的消息组装附近；保留 `backend/app/chat/service.py` 的限额、超时和上下文预算 |
| 6. 来源展示与删除联动 | 回答可显示文件名及可核实的页码/片段；删除会话或附件时清理对应向量 | 前端显示可点击来源；删除、重试索引和重建索引均能保持 SQLite 与 Qdrant 一致 |
| 7. 测试与回归 | 分别验证入库、检索、引用、隔离、故障与原有聊天 | 新增后端模拟测试及手动端到端验收；Qdrant 停机时返回明确错误或按事先确定的策略退回原问答 |

关键的执行路径是：

```text
用户上传文档 → 现有附件解析 → 切分片段 → Embedding 向量化 → 写入 Qdrant
用户提问 → 后端确认账号和会话可用附件 → 问题向量化 → 按权限过滤检索
         → 将命中的片段连同来源交给聊天模型 → 显示回答与来源
```

现有 `backend/app/attachments/context.py` 会把附件正文直接追加进模型消息。切换到 RAG 时，要明确何时使用检索片段、何时保留直接附文的旧路径，避免同一篇文档既全文塞入上下文又重复塞入检索结果。对于刚上传而尚未索引完成的文件，页面应显示“索引中”，或明确采用旧路径作为临时回退；不能悄悄假装已经检索成功。

## 四、数据分别放在哪里

| 数据 | 建议位置 | 原因 |
| --- | --- | --- |
| 用户、会话、消息、附件元数据及索引状态 | 现有 SQLite | 继续作为权限和业务状态的权威来源 |
| 原始文件、图片预览 | 现有 `backend/data/attachments`（或自定义数据库目录旁的附件目录） | 保持当前私有文件存储方式 |
| 文档片段向量与检索所需来源信息 | Qdrant 集合 | 用于相似度搜索；集合维度与 Embedding 模型输出一致 |
| 模型与服务密钥 | `backend/.env` | 不写进前端，也不提交 Git |

Qdrant 存储使用 Docker **命名卷**。在 Windows 上，不建议把 Qdrant 数据目录直接绑定到项目文件夹或普通 Windows 文件夹；Qdrant 官方说明这类挂载可能产生文件系统兼容问题。[Qdrant 常见错误说明](https://qdrant.tech/documentation/common-errors/)

**命名卷不是备份。** 以后若向量数据可以由原始附件完整重建，可以把“重建索引”作为恢复策略，但仍应一起备份 SQLite、原始附件和真实配置；若想快速恢复向量索引，还需要为 Qdrant 另定快照/备份流程。恢复或迁移时先停写，核对数据版本，不能只复制 SQLite 文件而忽略附件与 Qdrant 数据。

## 五、第一版 RAG 的验收清单

1. 上传一篇可解析文档，等待索引完成；提出文档中有明确答案的问题，回答附可核实的文件来源。
2. 询问文档没有提到的事实，系统明确说未找到可靠依据，不编造页码。
3. 同一用户切换会话后，不能检索到未授权在本会话使用的旧附件；换账号后不能检索到另一账号的内容。
4. 文档索引失败、Embedding API 失败、Qdrant 停机时有明确状态和可重试路径，不丢失原始附件与聊天记录。
5. 删除会话/附件后，对应向量最终被清理；重新索引不产生重复片段。
6. 原有纯文字聊天、图片提问、登录、聊天历史仍能正常使用。

## 当前最合适的下一步

先确定 **Embedding 模型与“检索范围只限当前会话文档”** 这两个设计决定，再开始写 RAG 代码。单纯建一个空集合没有实际检索价值；集合维度要由选定模型确定。之后按上面的阶段逐项实现和验收，而不是一次把现有聊天流程全部改掉。

参考：[Qdrant 本地快速入门](https://qdrant.tech/documentation/quick-start/)、[Qdrant 安全说明](https://qdrant.tech/documentation/security/)。本地自部署默认无认证，因此继续只把 `6333` 端口绑定到 `127.0.0.1`；若将来部署到其他机器或公网，必须重新设计认证、TLS 与网络访问控制。
