# 知言 AI 聊天历史实现与验收

日期：2026-09-17。接口版本：0.5.0。数据库结构版本：3。

## 使用方式

历史记录沿用当前 SQLite，新增 conversations 和 messages 两张表。登录后左侧显示自己的历史会话，可以切换、重命名、删除和加载更多。首条问题保存后，取前 30 个字符作为会话标题，用户可改成最多 80 字的标题，不额外调用模型生成标题。

点击“新建对话”先打开空白页面，发送第一条问题时才创建会话。刷新时通过地址栏中的会话编号恢复当前对话；没有编号时打开最近的会话。退出登录、密码修改和关闭页面不删除已保存的聊天，重新登录同一账号可以继续查看。旧版只存在页面内存、已经丢失的消息无法恢复。

页面默认加载最近 50 条消息，可点击“加载更早的消息”；会话列表每页 20 条，可加载更多。所有权由服务器检查，地址栏会话编号不能绕过账号权限。

删除需要明确确认，成功后永久删除会话及其消息；不会删除账号、其他会话或独立的调用计费元数据。正在回答的会话暂不能删除，需切换或新建对话结束本页等待，等状态更新后再删。

## 一次提问的流程

1. 前端只提交新问题、客户端消息编号和当前看到的最后消息序号。
2. 后端核对会话属于当前账号，检查是否有正在处理的消息，以及序号是否被其他窗口更新。
3. 短事务内保存 pending 用户消息，随后释放数据库写锁。
4. 从数据库读取最近 25 个成功轮次，排除失败的问题，再按现有字符预算裁剪；网络调用不占用 SQLite 写事务。
5. 模型成功后，在同一事务中保存 AI 回答、完成用户消息并更新会话时间。
6. 失败时保留问题并标为 failed，页面提供重新尝试或修改后作为新问题发送。

完整历史可以长期保存，模型每次使用的上下文仍受最近轮次、字符预算和模型自身限制约束。新界面取消了旧版页面的 25 次成功提问上限；个人每日额度和并发限制继续生效。

## 重试、并发和中断

- client_message_id 用于识别同一次问题。重复提交已完成的问题直接返回保存的结果，不重复插入消息或调用模型；同一编号不能换成另一段内容。
- 失败后的手动重试复用原问题编号；修改问题会保存一条新问题，旧失败问题保留但不进入模型上下文。
- 同一会话最多一个 pending 问题。expected_last_sequence 检测另一窗口追加消息，过期页面先刷新再发送，避免问题接到用户没看到的上下文后面。
- 超时或响应丢失后，前端先查询保存结果。无法确认时暂停提交并提供“重新加载会话”，不会自动重试模型调用。
- 切换会话取消本页的请求等待，旧响应不能显示到新会话。取消网络等待不保证模型供应商立即停止计算或计费。
- 服务异常退出后，pending 租约为 CHAT_TIMEOUT + 60 秒；过期记录在后续读取/发送时标为中断，允许手动重试。迟到的旧结果不能覆盖新尝试。
- 回答在其他窗口仍处理中时，本页每 2 秒查询一次状态；查询失败会停止自动查询并提示手动刷新。

## 接口

| 接口 | 请求或用途 |
| --- | --- |
| POST /api/conversations | 可提交客户端 UUID 字段 id；重复创建同一个 ID 返回同一会话 |
| GET /api/conversations | limit、cursor；按更新时间和 ID 倒序读取当前账号会话 |
| GET /api/conversations/{id}/messages | limit、before；before 为消息序号，读取更早消息 |
| PATCH /api/conversations/{id} | title；重命名自己的会话 |
| DELETE /api/conversations/{id} | 删除自己的会话及消息，成功 204 |
| POST /api/conversations/{id}/messages | content、client_message_id、expected_last_sequence、retry |

发送示例（两个 UUID 都应由当前请求或创建结果提供）：

```json
{
  "content": "请记住我叫小明",
  "client_message_id": "320bfb5b-3484-45fa-938f-1553676b1904",
  "expected_last_sequence": 0,
  "retry": false
}
```

响应包含 conversation、user_message、assistant_message 和 replayed。读取消息可查看 pending/completed/failed 状态，错误类别、模型和上下文裁剪提示也会保留。所有新增接口要求登录并检查浏览器来源；他人的会话与不存在的会话均返回 404。

旧 POST /api/chat 保留为已弃用的兼容接口，只做临时聊天、不保存历史；新网页使用会话接口。模型用量仍通过 GET /api/chat/usage 查询。

## 文件与数据库

- backend/sql/migrations/003_conversation_history.sql：新增会话、消息及索引，保留旧表和数据。
- backend/sql/schema.sql：八张表的完整建表定义。
- backend/app/conversations/schemas.py：请求校验和返回结构。
- backend/app/conversations/store.py：所有权、分页、消息顺序、事务、重试和租约恢复。
- backend/app/conversations/service.py：衔接历史记录与现有模型服务，处理保存失败和取消。
- backend/app/conversations/routes.py：历史接口。
- frontend/src/api/conversations.js：请求历史接口及处理登录失效。
- frontend/src/composables/useConversations.js：页面会话状态、发送、恢复、分页和迟到响应隔离。
- frontend/src/components/ChatWorkspace.vue：侧边栏历史列表和消息区域。
- frontend/src/components/ConversationDialog.vue：重命名与删除确认。
- frontend/src/history.css：历史列表、加载提示与操作弹窗样式。

conversations 使用 user_id 关联账号；messages 使用 conversation_id 关联会话，以 sequence 排序，并约束每个会话同一客户端编号最多一个问题和一个回答。request_id 仅用于关联调用统计，不设指向 model_calls 的外键，避免清理 30 天调用元数据时误删长期历史。

聊天正文保存在本机 SQLite 中，直到用户删除。数据库及备份属于私人数据，不应提交版本控制。保存历史不会将 `.env` 密钥、密码或 Cookie 加入聊天消息。

## 升级与验收

已编写功能代码和回归用例。本轮按用户要求仅执行静态检查，不运行功能测试、正式构建或真实模型/邮件联调；未主动操作实际数据库进行迁移或测试。

升级前先停止旧后端，保留现有 .env，建议执行备份迁移，然后启动：

```powershell
cd D:\code\project_python\wen_da
.\venv\Scripts\python.exe backend\migrate_db.py --backup
.\venv\Scripts\python.exe -m uvicorn app.main:app --app-dir backend --reload
```

启动也会自动迁移至版本 3。无需新增依赖或更换数据库。前端使用 pnpm dev；本轮未重新生成 dist。

人工验收建议：

1. 登录并提问一次，左侧出现标题；刷新后问题和回答仍存在，继续追问能使用前文。
2. 新建第二场对话，切换两场对话，确认内容互不混入；选中第一场刷新，应仍打开第一场。
3. 修改标题、取消删除、确认删除，检查只有确认后才删除目标会话。
4. 退出后用另一个账号登录，应看不到第一个账号的历史；改名、改密后仍可访问自己已保存的历史。
5. 模型失败后重试，用户问题不重复；修改后重新发送，旧失败问题保留。
6. 两个窗口打开同一会话，先后发消息；过期窗口得到更新提示，不应覆盖已有消息。
7. 查看多于 50 条消息和多于 20 场会话时的分页；切换会话期间旧响应不得串入新会话。
