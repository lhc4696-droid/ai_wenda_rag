# 流式聊天实现与验收

日期：2026-10-19。

## 1. 用户可见行为

普通聊天工作台默认流式显示回答，适用于默认百炼和个人 OpenAI 兼容模型，以及现有文档、图片附件与“查资料”模式。资料模式会先准备检索依据，随后开始增量输出。生成时发送按钮切换为“停止生成”。

回答按增量展示并渲染 Markdown；上下文裁剪和回答截断的提示在完成结果中保留。完整回答成功写入数据库后，页面使用服务端消息替换临时回答，刷新可恢复。

切换会话或新建对话不会中止原来的生成请求。客户端按会话保留增量与请求控制器；原会话在后台继续接收并保存回答，切回时恢复已有增量与停止按钮，完成后更新原会话的历史列表，不覆盖其他会话的消息或草稿。即使切换发生在新会话创建完成前，原问题和附件也会继续提交到所属会话。

主动点击停止只取消当前会话；退出账号、关闭或离开网页时统一取消本页仍在生成的请求。正常超时、模型错误和额度检查继续生效。

失败、停止或连接中断后，不把已经显示的半成品当成成功回答。客户端先查询历史，已完成的答案可直接恢复，明确失败的问题可手动重试，仍在处理中的问题会继续查询状态。重试复用原问题编号，不重复插入已保存问题；不会自动发起新的模型请求。

本次范围是普通聊天工作台。编程工作台继续使用已有任务、工具请求和结果协议。本次不新增模型输出上限能力，不改变本地文件权限，也不迁移业务数据库。

## 2. 接口契约

`POST /api/conversations/{conversation_id}/messages/stream`

使用登录 Cookie，执行原有来源检查。请求与非流式消息接口一致：

```json
{
  "content": "请解释这段内容",
  "client_message_id": "84647b16d1db4e03bfe07c620b140fa4",
  "expected_last_sequence": 0,
  "retry": false,
  "attachment_ids": [],
  "source_mode": "chat"
}
```

`client_message_id` 为本次问题的稳定 UUID，`expected_last_sequence` 来自已读取的会话版本。`source_mode` 沿用 chat/documents/legacy 的现有定义。不能只发送 content，也不能使用 GET EventSource 提交问题。

正常响应为 `text/event-stream`，每个 JSON 事件以 `data: ` 开始、空行结束：

| type | 含义及字段 |
| --- | --- |
| start | 接入流式连接，包含 conversation_id、request_id；不表示已经调用模型或保存答案 |
| content | delta 为新增文本，客户端按顺序拼接 |
| done | result 为完整 TurnResponse，包含 conversation、user_message、assistant_message、replayed；只有历史提交成功后发送 |
| error | message、error_code、status、retry_after、request_id；生成或业务检查失败 |

等待索引等阶段每 10 秒可发送 `: heartbeat` 注释。客户端忽略注释，不把它当成正文。

参数、登录、来源及模型配置依赖检查可能直接返回 HTTP JSON 错误；开始 SSE 后的业务失败通过 error 事件传递。不能只依据 HTTP 200 判断回答完成。连接结束却没有 done 时，必须查询历史确认，不能将增量内容作为最终答案。

重复提交已完成的问题返回 done 和原来的结果，`replayed=true`，不再次生成、不再次占额。

## 3. 服务端流程

`ConversationService.send` 共用原有消息幂等、所有者校验、序号检查、消息租约、附件准备、资料检索、错误标记与完整回答事务。流式仅增加增量回调；非流式接口继续保留。

`ChatService.answer` 共用上下文预算、模型选择、额度与并发检查、总超时、回答长度保护和用量收尾。流式回答的应用正文仍最多 20000 字符；供应商 finish_reason=length 或应用截断时，完成消息标记 answer_truncated。上游未正常完成且不是应用主动截断时，按失败处理。

SSE 发送层使用有限队列，避免慢客户端造成无界缓存。会话视图切换保持原 SSE 连接；主动停止或退出页面关闭连接后会取消模型协程，并等待消息失败标记与调用统计收尾。若完成事务已提交，则保留成功结果，由刷新恢复。停止本地请求不能保证供应商撤销已产生的费用。

默认百炼明确请求 incremental_output，避免累积块被重复拼接；个人兼容接口保留原有 HTTPS、DNS/SSRF 检查、精确代理白名单、禁止重定向等限制。客户端与兼容传输层处理跨包 UTF-8 和 SSE，拒绝异常或过大的数据，不透传供应商原始错误正文。

原 `backend/app/chat/streaming.py` 的重复路由和保存 TODO 已替换为共用会话业务的 SSE 呈现层，不再从该模块导入 app.main。

## 4. 运行和部署

沿用原来的启动方式，无新增生产环境变量、依赖或数据库迁移。更新后重启后端和前端开发服务器，再刷新浏览器。

开发与预览代理的等待时间统一为 225 秒；聊天客户端仍分别使用普通模式 120 秒、资料模式 210 秒的总等待上限。流式请求通过心跳保持空闲链路，超时仍需核对历史。

生产反向代理需允许持续转发 SSE，关闭此接口的响应缓冲，并设置覆盖业务等待时间的读取超时。例如将以下配置合并到现有、已配置 HTTPS 的代理位置：

```nginx
location /api/ {
    proxy_pass http://127.0.0.1:8000;
    proxy_http_version 1.1;
    proxy_buffering off;
    proxy_read_timeout 225s;
}
```

该片段只说明流式转发参数，部署仍沿用项目原有 Cookie、可信来源和持久化配置。

## 6. 手动模型验收

1. 启动项目并登录，发送能产生多段回答的问题，确认完成前已有文字，完成后刷新仍保留一组问答。
2. 用默认百炼和个人兼容模型分别验证；供应商必须支持各自接口的 streaming 能力。
3. 上传文字文档、图片，在已配置能力下发送；启用 RAG 时验证检索后的增量回答与参考资料。
4. 生成中切换或新建对话，确认原任务继续，其他会话草稿不被覆盖；切回原会话可继续看增量。主动停止后半成品不作为完成答案保留，问题可手动重试；关闭页面后后台生成被取消。
5. 验证中途断网、模型拒绝、限流、超时和输出截断；页面应提示实际状态，不悄悄重新调用模型。

真实供应商网络与计费效果由实际配置环境验收；上述自动化不使用用户 API Key。
