## 一、编程工作台：一个项目目录支持多个对话

状态：2026-10-13 已完成代码实现，待你手动验收。升级与验收步骤见 [项目目录与多对话](项目目录与多对话.md)。本次不实施第二至第五项的其他改动。

### 当前问题

改造前目录按“用户 ID + 对话 ID”绑定。“连接项目目录”按钮虽然位于聊天正文之外，实际仍然只是连接当前对话的目录。因此同一对话可以持续工作，但新建对话还需要选择文件夹，没有独立的项目管理层。

### 目标与待办

- [x] 建立独立的项目实体，一个项目绑定一个本地根目录。
- [x] 一个项目下面可以创建多个独立编程对话。
- [x] 新对话自动使用所属项目的目录；已有目录记录和浏览器权限有效时，不再重复选择或授权。
- [x] 权限失效、目录记录丢失等情况下，明确提示重新连接，不承诺永久无需授权。
- [x] 切换项目时同步切换对应目录和对话列表。
- [x] 同一项目中的对话共享实际文件，聊天记录各自独立；不默认复制其他对话的全部上下文。
- [x] 保留现有聊天布局、执行过程和本地修改展示。
- [x] 为已有会话与目录绑定设计兼容或迁移方式，避免丢失历史记录。

### 配套约束

目录访问仍由用户浏览器在授权范围内执行，后端保存项目、会话及任务元数据，不因此获得用户电脑的任意文件访问权限。

本次保留更严格的既有保护：同一账号最多一个活跃本地任务，同一浏览器站点通过 Web Lock 串行执行本地文件操作。支持多个对话，但不并发写文件。旧会话各自迁为独立项目，沿用旧会话 ID 作为项目 ID，兼容原浏览器句柄；不会依据同名目录自动合并。

## 二、输入输出限制与大文件生成优化

状态：优化方向已讨论，具体参数和实现方案待确认。

### 当前问题

用户生成较长 SVG 时遇到输出长度上限。输入上下文、模型单次输出、上传大小和文件工具限制是不同概念，需要分别管理，不能简单通过扩大上下文解决所有问题。

### 已核对的代码限制

以下是代码默认值或固定值，未核对当前运行环境中的覆盖配置，也不代表模型平台自身的能力上限。

| 项目 | 当前代码限制 |
| --- | --- |
| 普通聊天单个上传附件 | 默认 10 MiB |
| 上传文档提取正文 | 最多 16,000 字符，超出拒绝解析 |
| PDF 页数 | 最多 40 页，同时受正文长度限制 |
| 普通聊天输入上下文预算 | 默认 40,000 字符 |
| 普通聊天单次模型输出 | 默认 2,048 tokens，配置校验范围为 1～8,192 |
| 普通聊天返回正文 | 另有 20,000 字符上限 |
| 本地编程纳入处理的源码 | 最多 150 个文件、合计 2 MiB，单文件最多 128 KiB |
| 编程工具单次读取 | 最多 200 行、10,000 字符，可以分次读取 |
| 编程模型单次输出 | 固定为 4,096 tokens |

Token、字符和字节不能混用。工具调用参数里的代码或 SVG 也会占用模型输出预算。若报错为“模型输出达到长度上限，请缩小单次修改范围后重试”，对应代码在模型返回 `finish_reason="length"` 时终止该次调用；本次讨论未进行现场复现。

### 待办

- [ ] 分开配置普通聊天与 Coding Agent 的输出预算，取消编程输出固定为 4,096 tokens 的做法。
- [ ] 根据模型实际能力和接口兼容性设置预算，不对所有自定义模型使用同一个上限。
- [ ] 梳理前后端各项文件、消息、上下文及响应长度限制，统一管理并提供清晰提示。
- [ ] 大文件采用分段读取、分步生成和局部修改，减少一次输出完整复杂文件的情况。
- [ ] 评估分块暂存、完整性校验后写入机制，不执行被截断的工具调用，不把半成品当成成功结果。
- [ ] 对已有文件继续保留外部修改冲突检查及恢复能力，避免覆盖用户修改。
- [ ] 明确区分文件过大、输入上下文超限、输出截断和请求超时。
- [ ] 合理管理历史消息和工具结果的上下文预算，避免无限累加。

### 待确认事项

- 各项限制的目标值和可配置范围。
- 模型能力信息的配置与校验方式。
- 大文件分块生成、恢复及失败重试的具体实现。

流式输出可以改善等待体验，但不能自动突破模型的单次输出上限，不应作为本问题的唯一解决方案。

## 四、数据库与上线准备

状态：已给出建议，是否迁移及迁移时间尚未最终确认。

### 当前情况与建议

当前业务数据库使用 SQLite，数据访问代码直接使用 `sqlite3`，初始化时开启 WAL。上线并不强制要求更换数据库。

- 个人演示、小范围试用和单机部署可以继续使用 SQLite，配套持久化和备份。
- 面向多用户正式上线前，建议评估并迁移到 PostgreSQL。
- Qdrant 继续承担向量检索，不随业务数据库一起替换。
- 上传文件存储与业务数据库分别管理；用户授权的本地项目文件不因数据库迁移而搬到服务器。

### 如确认迁移，需要完成

- [ ] 先确定“项目—对话—任务”数据关系，再实施数据库迁移，减少重复修改。
- [ ] 调整数据访问层、数据库连接及事务处理，不是只改一个连接地址。
- [ ] 调整 SQL 和迁移脚本，验证约束、索引及并发行为。
- [ ] 设计旧数据迁移与回退方案，保留用户、会话、消息、任务和模型配置等数据。
- [ ] 保留与加密数据配套的密钥管理，避免迁移后无法解密已有模型配置。
- [ ] 建立备份、恢复及部署持久化方案。

数据库迁移只是上线准备的一部分，HTTPS、访问控制、密钥管理及服务运行配置也需要单独检查。

## 五、开启代理时自定义 API 不可用

状态：2026-10-12 已按用户后续要求实现受控本机代理配置；等待填写实际端口和可信 Base URL，并由用户进行网络验收。以下保留原讨论背景。

### 问题表现

用户确认开启代理后，默认模型可以使用，自定义 API 出现：

> 模型地址解析到了禁止访问的网络，请使用公开 HTTPS 服务。

目标是在代理保持开启的情况下，正常使用自定义 API，不要求每次关闭代理。

### 已确认的代码差异

| 项目 | 默认千问聊天 | 自定义 API |
| --- | --- | --- |
| 请求方式 | 百炼 SDK | 项目封装的兼容接口 |
| 代理环境配置 | `trust_env=True` | `trust_env=False` |
| 项目自定义的公网 IP 检查 | 不经过这套检查 | 经过 `PublicResolver` 检查 |

“是否读取代理环境配置”和“是否检查公网 IP”是两个独立设置，不存在前者自动决定后者的关系。代码差异不能证明默认请求实际经过哪条代理路径。

结合用户反馈，需重点处理 Fake-IP 与公网 IP 检查的兼容；本次没有读取实际域名解析结果或代理配置，不能据此认定具体客户端、模式和地址段。

API Key 用于模型平台验证调用者，不证明 Base URL 安全。请求由知言后端发出，因此需要限制其访问本机、内网等目标，以防 SSRF。此问题属于网络请求安全与代理兼容，不是 API Key 加密存储或数据库问题。

### 待处理方向

- [ ] 解决保持代理开启时自定义模型的连接问题。
- [ ] 梳理默认模型与自定义模型的代理行为，改善不一致的使用体验。
- [ ] 保留 HTTPS 证书验证和必要的目标访问限制，不直接删除安全检查或放行整个 Fake-IP 网段。
- [ ] 让连接测试、普通聊天与 Coding Agent 共用明确的自定义模型网络配置。
- [ ] 区分 DNS、代理连接、安全拦截和模型认证错误，给出针对性的提示。

### 已讨论、尚未选择的方案

1. **代理 DNS 配置方案**：让模型域名返回真实公网 IP，同时保留代理转发规则。Fake-IP 排除不等于必须直连，需要根据客户端与过滤模式配置。
2. **项目受控代理出口方案**：由后端部署者指定可信代理，不能由普通用户任意指定；代理模式下还需设计目标访问限制，不能只把 `trust_env=False` 改为 `True`。

当前本地后端可以使用本机代理；部署到服务器后，模型请求使用服务器的网络出口，不会自动使用访问网页用户电脑上的代理。

恢复处理时再确认代理软件名称、模式、监听端口和不含凭据的模型 Base URL。不需要提供 API Key、代理订阅链接或节点密码。
