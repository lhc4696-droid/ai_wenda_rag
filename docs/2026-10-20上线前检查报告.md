## 上线前应处理的 P1 问题

### 1. 发布版本缺少运行所需的文件

证据：`git status --short` 和 `git cat-file -e HEAD:<path>` 均确认以下文件存在于工作目录，但不存在于当前 HEAD：

- `backend/app/config_groups.py`
- `backend/app/integrations/endpoint_policy.py`
- `backend/app/integrations/compatible.py`
- `backend/app/model_settings/store.py` 及同目录其他模块
- `backend/sql/migrations/009_user_model_settings.sql`、`012_model_max_output_tokens.sql` 等迁移脚本

而 HEAD 中的 `backend/app/config.py` 已导入前两项，`backend/app/main.py` 已导入兼容模型和个人模型设置模块。仅将当前提交推送、拉取到服务器，无法重现本机运行状态，启动时可能直接报模块缺失；迁移脚本缺失也会阻止建库升级。

处理：确认正式发布的文件范围，将必要源码、迁移和测试完整纳入同一发布提交；排除实验文件、临时 SQLite 和本机凭据。在干净检出目录重新安装依赖、建空库、运行测试并构建前端。发布应固定到明确提交或版本标签。

### 2. 资料检索在额度检查前调用收费 Embedding

证据：`backend/app/conversations/service.py:49` 先执行 `rag.retrieve`，第 59 行才调用 `chat.answer`；聊天占额在 `backend/app/chat/service.py:106` 内执行。Embedding 调用没有经过 `ModelCallStore.reserve`。

离线复现：设置每日额度为 1，并预先消耗；上传文档后连续发送两次资料问答。

| 请求 | HTTP / 错误码 | 累计模拟 Embedding 调用 | 累计聊天模型调用 |
| --- | --- | --- | --- |
| 第一次 | 429 / CHAT_DAILY_LIMIT | 2（文档索引、问题向量） | 0 |
| 第二次 | 429 / CHAT_DAILY_LIMIT | 3（增加问题向量） | 0 |

这两次请求结束后，`model_calls` 仍只有预先消耗的 1 条记录。即使聊天额度已耗尽，仍可不断触发问题向量生成；换新文档还会产生索引调用。真实供应商会对这些调用按自身规则计费，而现有聊天次数统计无法覆盖。

处理：在任何外部检索/向量调用之前，原子校验和占用覆盖整轮资料问答的用户、全局额度及并发；保证完成、失败、取消都能释放。根据产品定义为 Embedding 单独计量或明确纳入整轮预算，并补充“额度耗尽时 Embedding 调用为零”的回归测试。改动时避免在后续聊天阶段重复占额。

### 3. 尚无可执行的完整生产部署配置

仓库根目录缺少后端 Dockerfile、前端 Dockerfile、Compose 文件、Nginx 配置和 `.dockerignore`。仅有旧编程沙箱的 Dockerfile，不承担 Web 应用部署。

`docs/docker-deployment-guide.md` 目前是需要手工复制的方案草稿，示例还包含：

- 第 56 行启动后端时使用 `--reload`，同时默认启动前端开发服务器。
- 第 364 行引用尚不存在的 `docker-compose.prod.yml`；末尾生产片段不构成完整可独立使用的服务定义。
- 示例中的初始化命令为 `python backend/init_db.py`，但示例镜像将 backend 内容复制到 `/app`，实际脚本会位于 `/app/init_db.py`。

处理：落地一套明确的生产配置，前端使用 `pnpm build` 的静态产物，后端关闭 reload、使用单 worker；配置 HTTPS、重启策略、数据卷和日志保留，并在干净环境实际构建启动。不能把文档示例视为已经验收过的一键部署入口。

### 4. 示例的环境变量没有完整传入后端

`docs/docker-deployment-guide.md:44` 的 backend 服务仅显式传入少数变量，没有 `env_file`。后面的 SMTP、EMAIL_CODE_SECRET、MODEL_CONFIG_SECRET、CORS_ORIGINS 和 QDRANT_URL 虽然写在根目录 `.env` 示例中，却没有被服务环境引用。应用只自动读取 `backend/.env`（`backend/app/config.py:16`，容器中对应 `/app/.env`）。

Compose 根目录 `.env` 用于变量插值，本身不会自动把全部键注入容器，见 [Docker 官方说明](https://docs.docker.com/compose/how-tos/environment-variables/set-environment-variables/)。

影响：按文档在干净服务器操作，验证码注册/重置、个人 Key 安全存储和 RAG 可能不可用；Qdrant 还可能继续指向后端容器自身的 `127.0.0.1:6333`。示例显式设置的 `SESSION_COOKIE_SECURE=false` 也不会因根目录 `.env` 写成 true 而改变。

本机配置还确认 `SESSION_COOKIE_SECURE=false`，且已填写本机自定义模型代理。若直接复制到云端，应先调整生产 HTTPS Cookie、实际域名来源以及云端出站网络；不能假定云服务器上也存在开发机的回环代理。

处理：用明确的运行时 `env_file` 或 secrets 注入生产配置；校验实际生效配置，HTTPS 下启用 Secure Cookie，并按功能核验 SMTP、加密密钥和 Qdrant 地址。新增生产预检时不要输出秘密值。

### 5. 构建示例会将本机凭据和数据复制进镜像

证据：部署文档第 134 行使用 `COPY backend /app`，仓库没有 `.dockerignore`；本机 backend 下存在真实 `.env` 和 data 目录。若直接从这份工作目录照示例构建，这些内容也会进入构建上下文和镜像。`.gitignore` 不负责 Docker 的上下文过滤，见 [Docker 构建上下文说明](https://docs.docker.com/build/concepts/context/)。

处理：增加 `.dockerignore`，排除真实环境配置、数据库、附件、备份、虚拟环境、测试产物和 Git 目录；Dockerfile 尽量仅复制应用源码、SQL 及依赖声明。密钥在运行时注入，数据通过持久化卷提供，不在镜像里保存。

### 6. 示例直接映射 Qdrant 和后端端口

证据：部署文档第 98 行为 `6333:6333`，未配置 Qdrant 身份验证；后端 `QdrantStore` 请求也未携带 API Key。`backend/app/rag/service.py` 的向量 payload 包含用户、会话、附件标识，以及文件名和文档片段原文。

如果云防火墙允许访问该端口，外部请求可以绕过应用的账号鉴权访问向量库。Qdrant 官方明确说明，自托管默认不启用身份验证或加密，见 [Qdrant 安全说明](https://qdrant.tech/documentation/security/)。

处理：首版将 Qdrant 放在容器内部网络，不配置公网端口映射；如需宿主机运维访问，仅绑定回环或使用受限隧道。应用后端也优先仅供反向代理访问，公网入口统一在 HTTPS 代理。若后续使用远程受保护的 Qdrant，需要为应用增加对应鉴权配置。

### 7. 容器代理下缺少可信代理配置，限流会误按全站统计

证据：认证路由多处使用 `request.client.host` 做 IP 维度的登录、发码和核对限流。示例 Nginx 设置了 X-Forwarded-For/Proto，但后端启动命令未配置可信代理。

检查本机安装的 Uvicorn：默认 `proxy_headers=True`，`forwarded_allow_ips='127.0.0.1'`。使用模拟容器地址 `172.20.0.3` 调用其真实代理中间件：默认配置忽略转发头，看到的是代理 IP 和 http；显式信任该代理地址后，才能识别原客户端和 https。

影响：Nginx 和后端在不同容器时，正常用户可能共用一个 IP 桶。例如所有用户合计每小时 20 次发码就可能触发 IP 限制，登录/注册也会互相影响。此问题与 SQLite 是否支持并发无关。

处理：按照最终网络拓扑明确设置可信代理地址或受控网段，并阻止公网绕过代理直连后端；核验实际 scheme 和客户端 IP。不要在公网可直连后端的情况下无条件信任任意来源转发头。依据：[Uvicorn 部署文档](https://www.uvicorn.org/deployment/)。

## 生产运行约束及后续改进

1. **首版必须单后端实例、单 Uvicorn worker。** `main.py` 启动时调用 `recover_interrupted`，后者无实例区分地中断全部活跃本地编程任务；运行中的任务和取消控制也存在进程内字典。`backend/README.md` 已声明该限制，部署配置需要落实。未来扩容时再引入任务队列、实例所有权和协调机制。
2. **备份和恢复需要形成实际流程。** 已有 `migrate_db.py --backup`，使用 SQLite 在线备份接口，这是可复用基础。但还需备份 `AUTH_DB_PATH` 同级的 attachments、向量数据或可验证的重建流程，以及单独保管的 MODEL_CONFIG_SECRET。真实附件路径由 `attachments/service.py:21` 决定，是数据库父目录下的 attachments；文档另挂载的 `/app/uploads` 不是当前服务实际写入路径。示例的 `/app/data` 整体持久化能覆盖默认附件路径。至少演练一次数据库、附件和密钥配套恢复；不要在迁移现有数据时重新生成模型加密密钥。
3. **区分存活和就绪。** `/api/health` 目前固定返回 ok，不检查数据库、文件目录或已启用服务的配置。可以保留这个低成本存活接口，再增加有界的就绪/配置检查；不应为每次健康探测调用收费模型或发送邮件。
4. **收尾浏览器测试失败及服务清理。** 常规附件下载用例预期 notes.txt、实际 content.json；需检查 mock 与真实接口行为的差异，不能将当前结果标记为全绿。真实后端下载测试的桌面和手机用例均通过，不据此掩盖失败用例。流式专项完成 12 项断言后，Windows 运行器未自动结束测试服务；本次按启动输出中的进程号及监听端口确认身份后，只停止了专项后端和前端，运行器随后以 0 退出，报告 12 passed。建议收尾时完善这一测试清理过程。
5. **可后续优化。** 本次前端 JS 主包约 605.17 kB（gzip 208.26 kB），构建有大于 500 kB 的提示，可按工作台/公式依赖拆分。Python 测试依赖有弃用提示，`pip check` 无冲突，优先级低于以上上线问题。后端部分依赖仍为版本区间，正式发布可生成和验收 Linux 生产依赖锁定结果。
