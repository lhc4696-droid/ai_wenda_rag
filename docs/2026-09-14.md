## 二、现有后端和数据库的梳理

### 1. 讲解了后端文件职责

结合现有代码，说明了各部分的作用：

| 文件或模块 | 职责 |
| --- | --- |
| main.py | 创建 FastAPI 应用、注册路由、处理公共中间件及应用启动 |
| config.py | 读取后端 .env 配置，包括千问、数据库和登录会话配置 |
| schemas.py | 规定聊天请求和响应格式，校验消息内容 |
| integrations/llm.py（原 services/llm.py，后续目录更名） | 通过 DashScope SDK 调用千问，提取回答并处理模型调用异常 |
| auth/routes.py | 注册、登录、查询当前用户、退出，以及登录状态检查 |
| auth/schemas.py | 账号请求格式校验和用户信息响应格式 |
| auth/security.py | 密码哈希、密码核验和登录令牌摘要 |
| auth/store.py | 账号、登录会话、账号请求限流的数据库操作 |
| tests | 使用临时数据库、模拟模型验证接口及认证逻辑 |

区分了“接口数据格式”与“数据库表结构”：schemas.py 负责接口数据校验，schema.sql 负责数据库表、约束和索引。

### 2. 说明了现有数据库的用途

当前 SQLite 包含三张业务表：

- users：保存账号、密码哈希和创建时间。
- sessions：保存登录令牌摘要、所属用户和过期时间；这里是登录会话，不是 AI 聊天记录。
- auth_attempts：保存注册和登录请求的限流计数。

同时说明了建表 SQL、初始化脚本、数据库读写代码与实际 .sqlite3 数据文件的区别。

**当前账号可持久保存，但聊天消息仍只保存在前端页面中，刷新后清空。**

### 2. Chat 已有登录保护，但认证文档不完整

当前采用 HttpOnly Cookie 登录会话，Cookie 名称为 zhiyan_session，不是返回 access_token 后手工填写 Bearer Token 的模式。

诊断时，不携带登录 Cookie 请求 /api/auth/me 返回 401；以空消息数组安全探测 /api/chat 也返回 401，提示先登录。该探测没有调用千问。

发现的文档缺口：代码直接读取 request.cookies，OpenAPI 中没有 securitySchemes，也没有为 chat 声明认证要求，所以页面没有完整展示认证方式。

后续可以补充 APIKeyCookie 等认证声明，并保留数据库中的会话有效性检查；今天没有实施此修改。[FastAPI 认证声明说明](https://fastapi.tiangolo.com/reference/security/#fastapi.security.APIKeyCookie)

## 六、邮箱验证码原理与开发演练

### 1. 原理讲解

- 通常所说的短信验证码和手机号验证码，是同一类通过短信验证号码接收能力的功能。
- 邮箱验证码采用相似流程，只是投递渠道变成邮件。
- 验证码核验不只是相等比较，还需要校验邮箱归属、用途、有效期、使用状态和错误次数。
- 正确性必须由后端判断；发送接口不能向前端返回正确验证码，也不能相信前端自行提交的“已验证”标志。
- 邮箱验证用于证明对邮箱的访问能力，不等于真实身份认证。
- 短信可以采用自管验证码加短信投递，也可以使用供应商托管核验服务；接口调用成功与验证码核验成功需要区分。

参考了 [OWASP 邮箱验证建议](https://cheatsheetseries.owasp.org/cheatsheets/Email_Validation_and_Verification_Cheat_Sheet.html) 和 [阿里云短信验证码核验说明](https://help.aliyun.com/zh/pnvs/developer-reference/api-dypnsapi-2017-05-25-checksmsverifycode)。

### 2. 按文件职责演练了实现顺序

1. 拆分账号请求格式：登录仍使用用户名和密码；发送验证码接收邮箱；注册增加邮箱和验证码。

3. 扩展用户邮箱字段，设计验证码记录表，并为旧数据库准备迁移。

5. 在安全模块中生成安全随机验证码，并处理与邮箱、用途和记录绑定的摘要核验。

## 七、聊天历史记录开发演练

### 1. 数据和接口设计思路

- 区分用户、聊天会话和消息，拟新增 conversations 与 messages 两张核心表。
- 每段会话关联所属用户，每条消息关联会话。
- 后端根据登录身份检查读取、发送、改名和删除权限，不能相信前端传来的用户 ID。
- 前端由提交整段历史，改为主要提交会话 ID、本次问题和请求 ID；上下文由后端读取数据库后组装。
- 页面历史与模型上下文是两件事：历史可分页查看，传给模型的内容仍需长度预算。

### 2. 按文件职责演练了实现顺序

1. 修改完整建表结构，并准备旧数据库迁移。
2. 拟建立独立 chat 模块，分别放置接口格式、数据库访问、业务流程和路由。
3. 数据库访问层负责会话和消息的查询、保存、改名、删除及防重复约束。
4. 业务层负责检查权限、保存问题、读取上下文、调用现有 llm 模块、保存回答和失败状态。
5. 在 main.py 注册聊天路由；迁移现有 /api/chat 时移除旧定义，避免重复；新增 PATCH、DELETE 时同步请求方法配置。
6. 前端增加会话 API 方法，调整 chat 请求参数。
7. 改造 useChat，管理当前会话、列表、消息、加载及请求状态。
8. 增加历史列表组件并接入现有聊天工作区，更新“刷新后清空”的页面提示。
9. 增加权限隔离、刷新恢复、重试、并发和删除等测试。

### 3. 特别说明的边界

- 新建对话不等于删除旧对话。
- 退出登录只清理页面状态，不删除数据库历史。
- 快速切换会话或账号时，旧响应不能串入新页面。
- 超时不等于服务端一定失败；重试前需要核对请求状态，不能无条件重复调用模型。
- 等待模型时不长期持有数据库写事务。
- 服务重启后不能让遗留请求永远保持“生成中”。
- 删除会话需要明确确认；演练中暂按生成中不允许删除设计。

上述均为设计演练，未新增聊天表、历史接口或历史列表组件。
