## 1. 总体判断

项目已形成有实际代码支撑的双工作台应用：普通聊天工作台负责聊天、附件和会话内资料检索；本地编程工作台负责项目、多对话和浏览器授权目录中的文件修改。账号、模型配置、调用额度和持久化为两者提供共用基础。

现阶段更需要完成已有能力的集成与验收，形成可信的稳定版本，然后再增加能力。主要问题集中在新旧契约未同步、实现与文档状态不一致、局部组件职责过多；现有 Vue + FastAPI + SQLite 架构可以继续演进。

当前应优先处理：配置重构后的测试失配、已注册但未完成集成的流式接口、RAG 的端到端超时和 Embedding 费用保护、尚未完整落地的输出预算配置。

本地编程的执行链是：用户提出需求 → 后端调用模型 → 模型返回工具请求 → 浏览器核验目录授权并读写文件 → 结果返回后端 → 模型继续或结束。后端没有因此获得用户电脑的任意路径访问能力。

已具备的基础包括用户隔离、聊天幂等与序号冲突检查、调用额度、附件解析隔离、个人模型 Key 加密、目标地址限制、本地修改冲突检查与恢复记录。后续应沿用这些边界。

## 3. 优先收尾事项

这里的 P0 表示继续扩展前优先收尾，P1 表示下一轮主线，P2 表示目标明确后实施。优先级不表示已发生线上事故。

### P0-01：配置分组重构与测试契约失配

**已确认的代码问题：** `Settings` 已聚合 `SMTPConfig`、`EmailCodeConfig`、`ChatConfig` 等配置对象，但测试仍使用旧的平铺构造参数和 `dataclasses.replace` 参数。属性 getter 只兼容读取，不能兼容构造和替换参数。

- `backend/tests/conftest.py:12` 仍向 `Settings` 传入 `email_code_secret`，而该项现在是属性，不是 dataclass 构造字段；同时遗漏必填的 `qwen_vision_model` 与 `qwen_coding_model`。
- `backend/tests/integration_app.py:26` 存在同类问题。
- 静态比对发现 18 处 `Settings(...)` 或 `replace(...)` 调用包含非构造字段，涉及附件、聊天额度、邮件、代理及 RAG 测试。

**影响：** 使用公共夹具的测试会在创建应用时失败，现有测试数量无法直接证明当前版本可靠。

**建议：** 保留一种明确的配置构造方式，更新测试工厂与嵌套配置替换方式，补齐必填参数；确认开发启动入口、测试入口与文档使用同一契约。

**完成标准：** 临时数据库与假模型下，相关测试能创建应用并运行；不读取或修改真实业务数据库，不调用真实模型和 SMTP。

### P0-02：流式输出已暴露接口，但尚未完成业务闭环

**已确认的代码问题：** 主路由在 `backend/app/conversations/routes.py:40` 注册了流式接口，但：

- 使用 `asyncio.sleep`，文件中没有导入 `asyncio`。
- 调用 `ConversationService` 中不存在的 `_save_turn`，并读取 `SendMessage` 中不存在的 `data.number`。
- 绕过正常的 `ConversationService.send` 与 `ChatService.answer`，没有复用现有消息幂等、额度预占、上下文裁剪、附件/RAG 准备及完整落库流程。登录和会话归属检查仍然存在。
- 对已经按时间正序返回的历史再次 `reversed`，会颠倒上下文。
- `frontend/src/api/streaming.js:31` 只提交 `content`，缺少后端必填的 `client_message_id` 与 `expected_last_sequence`，按当前契约会先被请求校验拒绝。
- 正式聊天界面仍通过 `historyApi.send` 调用非流式接口，没有接入这套流式客户端。
- `backend/app/chat/streaming.py` 另有未注册的重复实现，仍包含保存消息的 TODO 和不同的 Provider 方法名。

**影响：** 不能把流式输出列为已完成能力。即使修复表面的缺失导入和方法名，也仍需补齐业务保护。

**建议：** 先明确该版本是否交付流式功能。若暂缓，撤下未完成路由并标注文档；若交付，从现有会话状态和额度流程扩展增量事件，统一完成、失败、取消及刷新恢复行为。

**完成标准：** 同一请求重试不会重复保存和计费；附件、资料模式与普通模式行为一致；断连有明确状态；前后端能处理被网络拆分的 SSE 行与 UTF-8 字符；刷新后读到的状态与事件一致。输出端还需正确处理截断和用量元数据。

### P0-03：RAG 的超时链与费用保护需要补齐

**已确认的配置差异：** `frontend/src/api/conversations.js:24` 给资料模式 210 秒等待时间，RAG 本身可执行 75 秒，之后聊天默认最多 90 秒；但 Vite 代理的 `timeout` 和 `proxyTimeout` 均只有 125 秒。较慢的首次索引与回答组合可能先被代理切断。

**已确认的流程差异：** `ConversationService.send` 先调用 `rag.retrieve`，随后才进入 `ChatService.answer` 的模型额度预占。Embedding 调用没有在这条流程中纳入同等的预占和用量记录。因此即使后续聊天额度不足，仍可能已经发生向量化费用。会话内的消息互斥不等于全局 Embedding 并发与额度保护。

**建议：** 统一客户端、代理、索引、聊天及消息租约的总时间预算；为索引和查询向量化建立独立的额度、并发与用量口径，在付费调用前进行检查。

**完成标准：** 冷索引、热查询、Qdrant 离线和聊天额度耗尽均有明确结果；代理不会先于预期业务截止时间切断；能够解释一次资料问答的 Embedding 与生成调用成本。

### P1-01：输出上限只是部分实现，需把前后端和 Coding 统一起来

当前已存在迁移 012、`max_output_tokens` API 字段及个人聊天模型的读取逻辑，不能把这一项列为完全未开始。

但 `ModelSettings.vue` 没有对应字段的展示、编辑和保存逻辑；默认与个人 Coding 模型仍分别在 `coding/model.py:39`、`coding/compatible_model.py:24` 写死 `4096`。个人模型 API 禁止显式 `null`，还需设计已设置值如何清除并恢复默认。

**建议：** 分开定义聊天与 Coding 的输出预算，明确默认值、个人覆盖、恢复默认、后端校验及供应商能力限制。同步梳理输入字符数、工具参数、文件字节数、回答字符截断及超时，避免用一个 token 数代替所有限制。

大文件生成再单独推进：分段读取、局部修改、分块暂存、完整性校验和失败恢复。继续保持不执行被截断的工具调用、不覆盖用户外部修改。

**完成标准：** 页面保存后再次读取一致；实际发送给聊天与 Coding 的参数符合各自配置；恢复默认可用；超限错误能说明发生在哪一层。

## 4. 结构与文档整理

### 4.1 先拆编程工作台的业务协调逻辑

`LocalCodingWorkspace.vue` 当前共 2027 行，同时处理项目与对话、授权、轮询、工具执行、恢复、账号设置和多面板布局。建议围绕职责渐进拆分：

- 项目与对话状态。
- 目录连接和权限恢复。
- 任务执行、轮询、停止及过期。
- 文件修改记录和恢复。
- 目录树、过程面板、项目列表等显示组件。

已有 `local-files.js` 和 `coding-bindings.js` 保留为文件执行及绑定边界。先恢复测试基线，再逐步移动职责，避免同时改变交互和执行语义。

### 4.2 旧 ZIP Agent 应先解除共用依赖再归档

本地 `LocalCodingService` 仍继承旧 `CodingService`，后者还导入并创建 Docker 沙箱。旧 ZIP 入口虽然已下线，不能直接删除整个旧模块。

建议先提取共用的模型调用计量、worker 管理和取消收尾，再让旧沙箱实现与本地模式解耦。历史数据的保留与清理另行制定规则，不和源码整理一起删除。

### 4.3 建立一份可信的状态总表

当前材料存在明确冲突：

- 需求基线仍描述“不实现 RAG 或 Agent”，与现在的代码范围不符。
- 根 README 写迁移到 9，后端 README 写 11，代码 `CURRENT_VERSION` 是 12。
- 部分流式文档写“已实现”，但正式前端未接入、后端链路未完成。
- 移动端和 Docker 文档主要是方案或模板；当前仓库没有对应的 Android 工程及完整应用部署文件。
- `backend/backend/`、`backend/frontend/`、`backend/docs/` 出现额外模板、组件或报告，应确认用途后归并或归档。

建议状态统一为“设想 / 方案 / 部分实现 / 代码完成 / 已验收”，每项附入口、限制和验收记录。文档按当前说明、验收记录、历史方案区分；临时目录和演示素材明确是否保留、是否纳入版本控制。整理前先核对引用和数据用途。

## 5. RAG 下一阶段规划

目前是当前会话内的短文档 RAG：最多 10 份文档、单路密集向量检索、固定 Top 5。它已经具备分块、来源和权限过滤，但还不是跨会话可复用的知识库。

建议先确定资料属于“会话、项目还是独立知识库”。若只优化当前会话检索，无需先引入知识库实体；若需要复用资料，应先定义文档版本、授权、重建索引与删除传播规则。

随后用 `rag_ceshi` 现有资料建立固定题集，覆盖事实查询、跨文件、更新冲突、无答案和来源验证，记录预期证据与答案。重点观察：正确片段是否被检出、答案是否受到证据支持、无依据时是否说明、索引与查询耗时及调用用量。

按评测结果再决定调分块、Top K、相似度门槛，或增加关键词检索与重排。门槛需要结合实际向量模型和题集确定，不能凭一个固定分数认定可靠。索引有效性也可从当前的片段数量判断，逐步扩展到内容摘要、分块版本及模型身份。

## 6. 数据库与部署规划

业务关系已经建立：用户 → 普通会话 → 消息/附件；用户 → 编程项目 → 编程对话 → 任务。继续围绕这些实体演进。

本地演示及小范围单机使用可先保留 SQLite。当前本地任务 worker 保存在进程内，启动又会恢复中断任务，因此多 worker、多副本不能只靠更换数据库或增加 Uvicorn 参数实现。需要单独处理任务认领、租约、取消、互斥和清理者协调。

上线前应交付真正可执行的部署配置与恢复演练：

- 构建前端、反向代理、HTTPS、Cookie 和可信来源。
- 单 worker 运行约束、进程重启与任务中断行为。
- SQLite、附件、模型加密密钥的配套备份；Qdrant 快照或重建办法。
- 请求编号、错误类别、耗时和调用用量；健康检查与业务就绪状态的区别。
- 部署网络配置：当前 Qdrant 配置只接受 loopback 地址，多容器中的服务名访问需要明确调整，不能直接照搬方案模板。

当实际目标变成多实例、多进程或持续高并发写入时，再把 PostgreSQL 与数据访问层、事务、数据迁移和回退一起规划。数据库迁移本身不会解决进程内任务调度问题。

## 7. Kotlin 移动端规划

当前是已有方案文档，尚未形成可运行的移动工程。建议先交付账号、聊天历史、消息发送、附件及模型设置的最小可运行版本，再评估移动端编程能力。

先稳定后端请求、响应、错误码、幂等和流式事件契约；移动端保留独立界面，可复用业务接口。Cookie 的持久化、退出与改密失效、后台恢复和断网重试都需要实际验收。

浏览器的目录句柄、IndexedDB、Web Locks 和 File System Access API 不能直接搬到 Android。若移动端也要提供本地编程，应单独设计文件授权与工具执行适配层，明确文件来源、冲突和恢复语义。

## 8. 推荐实施批次

| 顺序 | 范围 | 可检查的交付物 | 进入下一批的条件 |
| --- | --- | --- | --- |
| 第一批 | 稳定基线 | 配置契约与测试修复；流式交付或暂缓的明确处理；当前能力与迁移版本总表 | 假模型与临时库回归通过，核心流程有验收记录 |
| 第二批 | 编程可靠性 | 聊天/Coding 输出预算闭环；编程组件逐步拆分；长文件处理边界 | 常规修改、截断、冲突、停止和恢复行为可验证 |
| 第三批 | RAG 优化 | 超时与 Embedding 费用保护；固定评测题集；基于结果的检索调整 | 有证据说明检索质量和成本变化 |
| 第四批 | 部署与恢复 | 可执行部署文件、持久化、备份恢复演练 | 新环境可按文档启动并恢复数据 |
| 第五批 | Kotlin 最小版本 | 可运行移动工程，复用稳定 API 的账号与聊天流程 | 真机完成登录、历史、消息与附件验收 |

若近期主要用于本地演示，第四批可以先完成最小运行和备份，不必立即公开部署；若目标是尽快手机使用，则在第一批契约稳定后，可把第五批的账号与聊天部分提前，但保持首版范围有限。

建议最近一次实施聚焦第一批。当前的限制主要来自集成和验证闭环，先获得一个能可靠回归、可说明已完成范围的版本，再继续扩展。
